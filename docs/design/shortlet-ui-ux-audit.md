## Scope and method

This audit records the Guest and Operator presentation, not business behavior. It uses (1) a live `npm run pilot:local` session against existing `.scratch/pilot-local/` data (not reset), (2) actual Chromium inspection at 320px, 390px, 768px and 1280px with `window.innerWidth` and `document.documentElement.clientWidth` confirmed, (3) screenshots captured to `.scratch/ui-ux-audit/screenshots/`, (4) the 41-screen accepted Rodney evidence in `.scratch/pilot-acceptance-rodney/`, and (5) source/CSS review to inventory the current system and compare behavior with the rendered view. At 320px, 390px and 768px the measured document width matched the viewport; the 1280px initial page also fit. The 768px viewport was measured live with the repository Chromium helper; captured tablet-state imagery is not in the evidence set.

The live pilot ran the deterministic local application and deterministic local payment path only. No Gemini request was made. Direct browser inspection covered Guest home, Abuja discovery, Unit detail, Request Draft, review, contact collection, Booking Request submitted, and safe fallback after an invalid post-submission refinement. A separate fresh CDP run authenticated an Operator and inspected inbox/detail; the opened detail was an older confirmed, non-actionable request. Accepted Rodney evidence supplies the current pending Operator detail plus confirm/decline, offer, payment, confirmed/declined booking, and restart/restored states. Rodney's 320px/390px screenshot-size behavior is an **environment limitation**: its report explicitly marks behavioral viewport checks skipped because CSS viewport did not change. This is not a product failure. New responsive measurements used actual Chromium emulation at 320px and 390px, plus a live 768px layout measurement.

### Google modern-web-guidance applied

The installed `modern-web-guidance` skill was invoked. Search/retrieve covered forms, accessibility and performance; its guidance informs this product specification as follows:

| Guidance class | Shortlet-specific application |
| --- | --- |
| Responsive design / content hierarchy | Compose the Guest surface as one narrow reading column; keep a booking workspace in-flow and single-column until space supports a calm two-column *content grouping*, never a permanent chat side canvas. At 320px, wrap amounts and long Unit names rather than shrink type. |
| Accessibility / keyboard and focus | Keep semantic landmarks and sequential headings, visible focus, associated field labels, focus restoration after a workspace change, WCAG contrast and 44px practical controls. Announce completed state changes once, not every model token. Validate the actual Weaver browser accessibility tree because A2UI `accessibility.label` does not reliably become DOM `aria-label`. |
| Forms | Collect phone/email in a short, visibly labelled task with inline, specific errors. Preserve valid values on retry/expiry. Do not use placeholder text as a label. Present amount and consequence before the submit action. |
| Navigation / interaction feedback | Make the current booking state and one next action explicit. Keep an always-findable “Back to conversation”/“Return to current request” control where context changes, and distinguish progress, waiting, error, and success. |
| Input/touch ergonomics | Meet ADR-0078's 44×44 CSS-pixel practical minimum for visible targets; use 16px or larger mobile input text to avoid unwanted zoom; keep the sticky composer and action buttons clear of browser safe areas and keyboard. |
| Image behavior / performance | Reserve image geometry, size sources to rendered width, eager-load only the first visible lead photo, defer below-fold gallery media, show the Unit facts before nonessential images, and use an honest fallback if a photo cannot load. |
| Constrained networks | Separate assistant/model wait from application-command wait and payment-provider handoff. Keep previously loaded facts visible during retries; never make the user infer whether a booking action completed from a spinner. |

## Proposed experience direction

Use the design principles in the system-direction document. The working visual proposition is **Abuja/Lagos residential hospitality, translated into a precise editorial marketplace**: warm off-white canvas, forest green for the action system, charcoal ink, one restrained clay/ochre accent, authentic listing photography and clear numeric rhythm. Keep screens calm with whitespace around decisions but compact where comparison requires it. Do not emulate chat products or big dashboard grids.

### Guest shell and transcript/history

- The conversation remains an ordered timeline. It explains, gathers intent and carries continuity; it is not the only place current booking state exists.
- The active workspace is the canonical current action area. Use one active surface; current booking stage, Unit, stay, amount and next action are legible without scanning the transcript.
- Focused surface can temporarily use more vertical room in the same shell; its return action restores conversation at the last useful position and restores focus predictably.
- Completed summaries remain permanently in the timeline as concise entries with state, Unit/date, amount where relevant, and a “View details” route/reference. Never delete meaningful history.
- A surface superseded by a newer revision is no longer interactive. Retain a single compact history row (“Earlier search · 2 stays · 22 Sep”) with expand/details affordance rather than a “superseded” divider for each old workspace and a duplicate transcript paragraph. Surface may be revisited only via a read-only safe projection; fresh server state required before action.
- Historical discovery result narration is collapsed after newer refinement; the last user intent and latest result count remain visible in history. Do not repeat full price facts in timeline and active result card.
- Status transitions enter history once and update the persistent active status. For example “Request sent” is a one-time timeline event; active card says “Waiting for Operator response” with current deadline.
- Keep the sticky composer while ordinary exploration is occurring; once an active form or consequential review requires focus, it may compact or temporarily collapse but preserve typed draft. Mobile keyboard must not cover the focused field/action. Restore the conversation composer only after the user exits the focused flow.
- Model wait says what is happening in plain language and can be canceled only where operation semantics allow. Application commands use action-specific progress (“Sending Booking Request…”) and prevent duplicate submission while authoritative outcome is pending. Payment handoff says “Opening hosted card checkout”; returning does not show paid until verified.
- Provider unavailable leaves existing projection/history intact and offers retry plus conventional search/status access. No token-stream-by-token announcement; meaningful update is polite, critical session expiry assertive.

### Discovery card and Unit detail specifics

**Card priority:** (1) lead photo, (2) human Unit name, (3) neighbourhood + city, (4) concise bedrooms/bathrooms/guest capacity and “Entire Place”, (5) All-In Stay Total for the exact selected stay, (6) separate Refundable Security Deposit when one applies and any specified immediate cash/authorization requirement, (7) up to three genuinely useful amenity labels, (8) supported requestability/open-date qualifier, (9) “View Unit”. One prominent number, one primary button. Don't print all fee rows and cancellation policy on discovery card; detail/quote review contains the auditable breakdown. Nightly average is optional secondary context only, derived from total and labelled as an average including mandatory charges; suppress when it does not aid comparison. No “Available” certainty from open dates; phrase “dates open to request; Operator confirmation required”.

**Unit detail order:** gallery; title; location; type and facts; relevant summary; price area; disclosure of deposit/Amount Due Now; amenity groups; description; inspection claim and dates/scope; relevant policy; Request to Book. At 320px use 16px minimum side gutters, one-column media/detail, no clipped controls and a wrapping money row. At 390px same structure with larger breathing room and optionally a side-by-side compact facts line if it wraps naturally. Tablet may place gallery and key facts in a two-column composition, but keep order linear for reading and price/action associated. Desktop uses a bounded reading column with a gallery rail or grid and an adjacent summary only when it does not duplicate the transcript; no separate Guest product. At all sizes retain keyboard order matching the visual sequence.

### Booking and money-state language

Use this product-level sequence label set; actual stage remains authoritative:

1. **Draft — not submitted; no dates reserved.** A Request Draft is Guest intent, not a Booking Request.
2. **Request sent — waiting for Operator response.** State exactly the authority-projected inventory block, the 30-minute response deadline where that disclosed request has begun, and that there is not yet a Reservation.
3. **Offer issued — Operator confirmed availability.** Conditional Booking Offer is not itself Reservation; show expiry and terms.
4. **Payment required — booking not confirmed yet.** Payment Window deadline appears as absolute WAT; hosted provider handles card details.
5. **Payment processing — checking provider confirmation.** Browser return is not proof; retain current transaction details and communicate next check/reconciliation path.
6. **Reservation confirmed — payment verified.** Use only after authoritative success; identify contract/Reservation clearly.
7. **Request declined / Offer expired / Payment under review** are separate terminal/degraded language, not blended into a generic error.

Every price view puts **All-In Stay Total** first for the chosen dates and party. Itemize accommodation subtotal and each mandatory fee/tax only when authoritative quote provides them; their sum must reconcile to All-In Stay Total. Deposit appears in a separate row labeled **Refundable Security Deposit** and stays excluded from All-In Stay Total. **Amount Due Now** is shown only when supplied by the current artifact and states whether it includes the stay payment and deposit/selected extras. The payment CTA includes the exact amount (“Continue to hosted checkout · ₦…”) where its width and current amount permit; do not abbreviate to “Pay now” if amount omission would create ambiguity. Use Nigerian grouping and locale (`₦202,000.00` or `NGN 202,000` according to consistent app formatter; choose one format in implementation, use it everywhere, and never show competing representations in one panel). Dates use `29 Sep – 1 Oct 2026`; deadlines use e.g. `22 Sep 2026, 5:17 pm WAT (Africa/Lagos)` if the exact authoritative value is available. Do not invent price rows, amounts, cancellation refunds or deposit return timelines.

### Trust and safety copy rules

- A unit-specific dated physical inspection may be represented as “Inspected on [date]” with scope; do not call it safe, fully verified, guaranteed, or independently certified.
- Operator confirmation is an availability commitment/state, not a platform guarantee and not a Reservation.
- Payment copy may say the Guest leaves Shortlet for a hosted card checkout (Paystack selected by ADR-0087) only in the context where this capability is actually enabled. Do not state “100% secure”.
- Contact collection is coordination/booking contact; it is not Guest identity verification. Do not suggest that phone/email collection proves ownership.
- Online identity verification is not required to request/book in this pilot. Do not show “Verified Guest” or KYC gates in booking UX. Identity verification and physical access remain separate check-in concerns; Reservation confirmation is not access authorization.
- No testimonials, ratings, volumes, insurance, guarantee, provider partner marks, or safety claims until evidence and permission exist. Design empty social-proof module as omitted at launch or clearly marked internal placeholder, never guest-visible fake proof.

## Accessibility, network and open evidence

The detailed target matrix is in [shortlet-design-system-direction.md](shortlet-design-system-direction.md). Critical acceptance includes 320px reflow at 200% zoom; keyboard-only complete journey; focus restored to current workspace heading or action after replacement; accurately labelled native contact inputs; status announcement after projection change but not streaming token; descriptive actual room photo alt text; non-color status; reduced-motion preference; and 44×44 target measurement. Run manual screen reader checks in representative browser/AT combinations and inspect rendered DOM/AX tree after Weaver output rather than assume metadata mapping.

Text, state, amount, deadline, CTA and fallback come before below-fold photos or decorative assets. Reserve each media box's ratio to prevent layout shift; responsive sizes fit mobile card/detail widths. Eager/high priority only first viewport's lead photo, lazy-load offscreen gallery/result photos; no font service dependency by default. Distinguish model, application command and provider redirect latency. Use helpful status text and an idempotent retry/current-state route; preserve composer and contact draft. Offline errors make no claim of submission until server state confirms; after reconnect, query current authoritative state instead of blindly resending.
